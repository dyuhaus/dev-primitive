# builder lessons

This is durable, harness-neutral working knowledge for the `builder` profile.
Keep behavioral, reusable lessons here; do **not** store secrets, credentials,
personal data, private task content, or chronological task logs.

**Do not hand-edit this file to record a lesson.** It lives in a branch-mutable
tree, so appending to it is a read-modify-write that a branch switch can silently
undo. Record lessons with:

```bash
python3 "$DEV_PRIMITIVE/lessons.py" add --key builder --task "<task type>" \
  --lesson "<reusable lesson>" --evidence "<path, command, or measurement>"
```

See [PROFILE.md](./PROFILE.md) for the same command in context. A bare
`python3 lessons.py` only works from the checkout that holds the script.

`lessons.py promote` is the only route from the inbox into this repository, and
it is **run by a person** who reviews the diff and commits it — not by an agent
mid-task, and not from a background job. Hand edits to this file are for one
thing: consolidating dated entries into `## Durable practices`.

## Durable practices

- Read the profile and applicable project instructions before work.

- 2026-07-28 | HTTP handlers that abort a request mid-upload | When a server responds and then destroys the socket (413 on a body cap, 429 mid-stream), it MUST also send `Connection: close`. A keep-alive client returns the already-dead socket to its pool, so the failure lands on the NEXT, unrelated request as an opaque "socket hang up" — the test that breaks is not the test for the code you wrote, which sends you debugging the wrong handler. Ordering matters too: write the status first and destroy only after the response's `finish` event, otherwise the client gets a reset with no status at all. | dy-bridge `readBodyCapped`: the 413 assertion passed while the following POST died; adding `Connection: close` to that one response fixed it, and a browser would have hit the same thing.
- 2026-07-28 | adding a network call to an existing static page | Read the page's own `Content-Security-Policy` BEFORE writing the fetch, and prove the policy edit is load-bearing with a negative control that serves the original policy. - 2026-07-28 | verifying a fix whose symptom is a POSITION, SIZE, or ACCUMULATED value | When the observable is a number that drifts over time, a passing assertion is worth nothing until you prove the number was somewhere else first. - 2026-07-28 | new branching/gating logic + its tests | When a freshly written suite for new decision logic goes green on the FIRST run, it has not yet been shown to test that logic — fixtures can pass because the code path was never entered. - 2026-07-30 | resuming work on a branch whose PR was squash-merged | Before committing onto an inherited branch, diff it against the REMOTE default branch, not against its own base: `git diff --stat origin/main..HEAD`. A PR opened from it silently REVERTS those files, and none of the usual checks show it: `git status` is clean, `git show --stat HEAD` lists only your paths, and the tests pass because the reverted file is documentation. - 2026-07-30 | porting an input-validator / sanitizer | A validator's POSITIVE control must be produced by the application's own writer, not hand-written in the test. - 2026-07-31 | changing a gate/policy whose justification is a stated assumption | When a decision rule is justified by a claim about a person's behaviour, the acceptance test is that person's real decision history, not a fixture — and check first whether the claim contradicts the system's own reason for existing, because that inversion reads as sound in code review and is obvious in the data.
